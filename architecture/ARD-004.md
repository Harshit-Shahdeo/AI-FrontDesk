# WhatsApp Integration

**Version:** 1.0

**Status:** Implemented

**Author:** AI FrontDesk Engineering

---

# Purpose

The WhatsApp Integration module serves as the communication gateway between AI FrontDesk and the WhatsApp Business Platform. Its primary responsibility is to receive customer messages from Meta, convert them into our internal format, and provide a clean interface for the rest of the application.

The purpose of this module is to isolate the core business logic from Meta's APIs so that internal services never depend directly on external webhook payloads.

---

# Problem Statement

Meta delivers incoming WhatsApp messages through webhook events. These events contain deeply nested JSON structures that are designed specifically for Meta's platform.

Directly using these payloads throughout the application would tightly couple AI FrontDesk to Meta's implementation. Any changes introduced by Meta would require modifications across multiple modules, making the system difficult to maintain.

To solve this problem, AI FrontDesk introduces an Anti Corruption Layer that transforms Meta's webhook payload into simple internal objects before the data enters the application's domain.

---

# Goals

The WhatsApp Integration module should:

- Receive webhook requests from Meta.
- Verify webhook ownership during setup.
- Parse incoming webhook payloads.
- Convert Meta payloads into internal DTOs.
- Ignore unsupported webhook events.
- Keep business logic independent from Meta's JSON structure.
- Provide a clean integration point for future messaging providers.

---

# Non Goals

This module is **not** responsible for:

- AI response generation.
- Conversation management.
- Appointment booking.
- Customer management.
- Business validation.
- Message history.
- Database persistence.

Its responsibility ends once a valid incoming message has been transformed into an internal object.

# Components

## Webhook Controller

The controller exposes the public endpoint that Meta communicates with.

It has two responsibilities.

### GET /webhook

Used only during webhook verification.

Meta sends a verification request containing a challenge value. The controller forwards the request to the service layer, which validates the request and returns the challenge back to Meta.

### POST /webhook

Receives every webhook event generated by Meta.

The controller performs no parsing or business logic. It simply forwards the request to the service layer.

---

## Webhook Service

The service coordinates all incoming webhook requests.

Its responsibilities include:

- Verifying webhook requests.
- Calling the appropriate parser.
- Logging incoming messages.
- Returning responses expected by Meta.

The service never parses raw JSON directly.

---

## WhatsApp Message Parser

The WhatsApp Message Parser acts as the Anti Corruption Layer between Meta and AI FrontDesk.

Its responsibility is to convert Meta's webhook payload into an internal `IncomingMessageDto`.

### Example

Meta sends:

```json
{
  "entry": [
    {
      "changes": [
        {
          "value": {
            "messages": [
              {
                "from": "919999999999",
                "text": {
                  "body": "Hello"
                }
              }
            ]
          }
        }
      ]
    }
  ]
}
```

The parser converts it into:

```ts
IncomingMessageDto {
    phoneNumber: "919999999999",
    message: "Hello",
    messageId: "...",
    timestamp: Date
}
```

After this point, no other module in AI FrontDesk has any dependency on Meta's webhook structure.

---

## Webhook Verification Parser

Webhook verification follows a completely different payload structure from incoming messages.

To keep responsibilities separated, verification is handled by a dedicated parser.

It extracts:

- mode
- verify token
- challenge

Separating verification from message parsing keeps both implementations simple and easier to maintain.

---

# Data Contract

Every incoming WhatsApp message is represented internally using the following DTO.

```ts
IncomingMessageDto

phoneNumber
message
messageId
timestamp
```

Every downstream module consumes this object instead of Meta's original webhook payload.

# Anti Corruption Layer

The Anti Corruption Layer protects AI FrontDesk from changes introduced by external providers.

Instead of exposing Meta's webhook payload throughout the application, all external data is transformed into simple internal objects.

This approach provides several benefits:

- Business logic remains independent from Meta.
- Future API changes affect only the parser.
- Internal modules remain clean and provider agnostic.
- Future messaging platforms can be integrated without changing the application's core logic.

---

# Error Handling

The module handles several failure scenarios.

| Scenario | Response |
|----------|----------|
| Invalid verification request | 400 Bad Request |
| Invalid verification token | 403 Forbidden |
| Unsupported webhook event | Ignored |
| Malformed payload | Safely discarded |

The module should never allow malformed webhook requests to crash the application.

---

# Security Considerations

Webhook ownership is verified using a shared verification token.

Sensitive credentials such as:

- Access Token
- Verify Token
- Phone Number ID

are stored in environment variables and are never committed to source control.

Only verified webhook requests are accepted.

# Design Decisions

The following architectural decisions were made during implementation.

- Controllers remain thin and contain no business logic.
- Business logic is isolated inside the service layer.
- Parsing is delegated to dedicated parser classes.
- Verification and message parsing are implemented separately.
- Internal modules never depend directly on Meta's webhook payload.
- Meta is treated as an external integration rather than part of the application's domain.

---

# Conclusion

The WhatsApp Integration module provides a clean and maintainable boundary between AI FrontDesk and the WhatsApp Business Platform.

By introducing an Anti Corruption Layer, the system remains resilient to external API changes while allowing the core business logic to evolve independently.

This architecture ensures that future enhancements such as AI conversations, appointment booking, and multi tenant support can be built without introducing dependencies on Meta's webhook implementation.
